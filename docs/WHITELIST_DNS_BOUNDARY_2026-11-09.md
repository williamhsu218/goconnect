# 白名单模式的 DNS 边界修正（2026-11-09）

## 现场与配置恢复

安装版 1.0.11 / 71 在公司物理网络中使用 HY2 白名单线路，公司副连接已禁用。名单内为 AI 应用及服务，浏览器不在名单中。内网 IP 可达，公司原 DNS 能返回预期私网地址；系统默认 DNS 却由 GoConnect 的代理 DoH 返回公网地址。直接绑定物理网卡的公司 HTTP/HTTPS 均返回 200。故障在解析策略，不能归因于副线阻断或服务器不可达。

最初准备独立公司线路的处理偏离了用户要求。新增的未启用副本已经通过正常界面撤销；原有 7 条线路、全部三份配置文件哈希及主线路进程身份均恢复或保持不变，没有切换线路和中断 VPN。用户要求白名单本身遵循应用边界，不增加公司域名例外。

## 源码修正

此前 `configureManagedDNS` 对所有模式使用同一策略：默认解析和 `direct-nameserver` 都走代理 DoH。它不能使名单外浏览器使用公司原 DNS，普通连接的进程规则与解析出口不一致。

白名单候选改为延迟解析：

- 共享系统查询的普通 A/AAAA 先返回内核本地映射，不先替所有应用发出代理 DNS 查询。
- 后续连接仍由现有应用规则判断出口；代理分支传递域名到认证代理，直连分支通过原网络解析器解析，并保留原接口绑定。
- 本地域名、用户已有直连域名、原有 supplemental DNS 域保留真实答案与专用解析器；不扩充用户配置。
- IPv4 映射池使用内核默认的 `198.18.0.0/16`，IPv6 使用不包含既有控制地址的独立池。全局模式保留原有代理 DoH、失败不回退和原 DNS 例外策略。

这是连接选路后的域名解析，不是声称每个独立 DNS 查询都能从 macOS 共享解析进程中恢复原 App 身份。独立 DNS 工具可看到映射地址；应用自带加密 DNS 等仍按既有边界另验。

## 验证与当前状态

- 真实打包内核隔离测试通过：共享查询不进入原 DNS；同一未预先配置的公司测试域，代理分支收到原域名，原 DNS 查询数保持零；直连分支使用原 DNS 并到达不同本地服务；代理失效不回退到直连 DNS。
- 测试用两个入口确定选路结果，避免把普通用户下回环 SOCKS 无法识别进程的结果伪装成实际 App 归属验证。之前一次回环进程规则探测未取得进程身份，保留为未通过。实际进程归属、系统 TUN、双栈及连接切换仍须安装后单独验收。
- 原有全局 DNS / DoH 失败保护隔离测试继续通过。全套适用 Go race 通过；专用原生 TUN 门禁未启用，不计为通过。
- 本轮只构建候选，不升级版本、不安装、不发布，不改变正在运行的 App、网络服务或默认 DNS。先前公司 socket 清理修正也仍仅在源码中。
