# HTTPS / UDP 高负载超时复查与 0.11.12 候选

日期：2026-10-18。约束：保留正在运行的真实 VPN 和用户配置，不重启服务、不切换路由策略。

后续进展：用户随后授权维护窗口，0.11.12 已安装并更新服务。实际 14 分钟渲染和两次隧道恢复通过，但 UDP 仍有超时，未提升正式版。完整安装、实时运行与抓包边界见 [0.11.12 真实 VPN 验收记录](CANDIDATE_INSTALL_0.11.12.md)。下文保留维护窗口之前的原始调查阶段，不把当时的“尚未安装”当作当前状态。

## 结论

发现并修复了一处明确的服务调度配置问题：GoConnect 将实时网络服务声明为 `ProcessType=Background`。已安装的 launchd 文件及运行进程证实，该策略使特权服务、worker 和 Mihomo 以优先级 4 运行；应用侧 OpenConnect / GoConnect bridge 为 31。实时转发依赖的任务不应按无用户交互的后台作业调度。

源码候选 0.11.12 / build 49 将服务改为 `Interactive`。服务通过经过认证的 Unix socket 接收请求，没有可供 `Adaptive` 追踪的 XPC transaction。修复不设置实时调度、不调整 nice、不改全局内核参数，也不放宽健康检查、租约或隧道恢复期限。

**这不等于所有请求超时的唯一根因已经证明，也不等于新版本已在当前 VPN 生效。** 透明分流的严重迟延有直接现场证据；另外三次 SOCKS UDP 超时绕过了后台 Mihomo，必须保留为尚未唯一归因的请求级失败。正式分发包仍为 0.11.11，回滚包仍为 0.11.10。

## 当前真实 VPN：不注入故障的 10 分钟重测

两个 FFmpeg 动态 4K / 30 fps / libx264 medium / 每路 8 线程编码任务持续 **600.081 秒**，探针总计 **660.221 秒**。287 次负载期整机采样：CPU 平均 **98.66%**，峰值 100%，1 分钟负载最高 56.72。两个渲染进程在全部负载期采样中均存活。

没有向正在使用的 VPN 进程发送暂停、重连、终止信号。应用、OpenConnect、bridge、worker、Mihomo 的会话身份没有变化；路由状态始终 `ready`，租约最大陈旧时间约 0.997 秒。探针自身调度延迟最大约 71 毫秒，没有出现整机完全停止调度的证据。

| 路径 | HTTPS | UDP | 观测 |
| --- | --- | --- | --- |
| 当前透明分流 | 319/319 | 129/130 | HTTPS 最大 6.787 秒，UDP 一次 15 秒超时 |
| 直接访问 GoConnect SOCKS | 330/330 | 123/126 | HTTPS 最大 0.702 秒；一个 UDP 流连续三次无响应，随后相同本地端口恢复 |
| 物理网卡绑定直连对照 | 330/330 | 132/132 | HTTPS 最大 0.188 秒，UDP 最大 0.278 秒 |

直连 `1.1.1.1:443` 在空载预检就不可达，因此直连 HTTPS 使用可达的 `www.apple.com`；它不是同一站点的严格链路 A/B。UDP 三条路径都使用预先解析的同一 Cloudflare STUN IPv4 地址。绑定只作用于探针 socket，没有改系统路由。透明 HTTPS / UDP 的实际 Mihomo 连接记录均为 `Tun → GoConnect`；SOCKS HTTPS 出口摘要也与透明路径一致。

透明 HTTPS / UDP 多次同时延迟 3–7 秒，而 SOCKS HTTPS 与直连正常。服务同时记录 `route.get4` 6.303 秒超时、7.751 秒迟到成功，以及多个慢路由查询。这将该类共同迟延定位到透明转发 / 后台 worker 一段。Mihomo 栈采样及内核 stackshot 直接记录优先级 4 和 runnable 等待线程；OpenConnect 的采样主要为正常 I/O 等待。

系统日志中的热预算和崩溃报告活动没有证明它们是起因。Mihomo 的 Go 函数表可以还原 `sing-tun` / gVisor 位置，但仅看到 `RawSyscall` 不能证明死锁或缓冲耗尽，本次没有据此修改第三方核心。参考对应版本的 [Darwin raw I/O 实现](https://github.com/MetaCubeX/sing-tun/blob/v0.4.22/internal/rawfile_darwin/rawfile.go)；服务任务类型语义以本机 `launchd.plist(5)` 的 `ProcessType` 说明为依据。

本轮结论：**VPN 会话抗误断通过；请求零超时未通过。** 不能把 UDP 原始报文未返回直接等同于 VPN 断线，也不能将未抓到包级链路证据的请求丢失归因于服务器限流。

## 修复、保护和验收范围

- `networkServicePlist` 改为 `Interactive`。新增平台解析测试，使用 macOS `plutil` 校验实际生成的 XML，同时核对服务身份、版本目录、KeepAlive、重启节流、退出期限和 umask。
- 新增可复用只读 `script/request_probe.py`，证据强制写到项目外的新目录。它不会写用户配置、切换 VPN、修改路由或操作已有进程生命周期。会话 token 仅用于内存中的本地认证，日志不保存 token 或响应正文。
- 四项探针回归覆盖迟到事务、持续不匹配时的绝对期限、错误头 / 长度，以及超过期限的正确响应不能被算作成功。
- 已在渲染压力期间重跑带竞态检测的保护测试：30 秒只读健康检查窗口、租约过期 / owner 消失 / PID 复用、真实网络或网关变化、写路由异常、75 秒恢复上限、认证 / 证书 / 服务器终止以及取消保护。
- 旧版与候选完整验收结果分开记录；未在当前公司 VPN 上伪造认证失败或修改服务器策略。

任务类型对照使用同一已安装 Mihomo 二进制、相同真实 VPN SOCKS 上游、相同 probe，分别通过独立的 `Background` 和 `Interactive` launchd 作业启动。测试实例禁用 TUN 和 DNS，不安装路由，也不替换当前 service；临时认证配置、launchd 作业和视频在结束时清除。该对照能验证策略和普通 TCP/UDP 转发兼容性，**不能代替新服务接管实际 TUN 后的验收**。

对照持续 **410.748 秒**，前段与上述原渲染重叠，随后两路新 4K 编码连续 **300.307 秒**；新渲染在全部采样中存活，1 分钟负载最高 50.58。实际调度优先级分别为 4 与 31。该阶段未单独记录整机 CPU 使用率，不能套用上一轮 98.66% 的平均值。

| 任务类型 | HTTPS 成功 / 总数 | HTTPS 最大耗时 | UDP 成功 / 总数 | UDP 最大耗时 |
| --- | --- | --- | --- | --- |
| Background | 200/200 | 3.152 秒 | 81/81 | 6.185 秒 |
| Interactive | 202/202 | 1.002 秒 | 81/81 | 0.574 秒 |

两组 HTTPS 都维持同一连接，UDP 本地端口没有变化。结果支持后台限流对转发迟延有实质影响；两组本次均无失败，不能单独证明原事件的每一次超时均由此引起。两个临时 launchd 作业均已移除，临时视频、凭据配置和测试目录均已清理。

简单对测试实例执行 `taskpolicy -B` 后优先级仍为 4，说明不能以它冒充 launchd 任务类型已经修正。没有对当前 VPN 的进程应用这个操作。

## 生效与保留边界

正式生效需要安装候选并更新特权服务。服务安装器的 capture lock 明确拒绝在 VPN 使用中替换服务；本轮保留该保护，未绕过它。因此需要一个允许短暂重新连接的维护窗口，才能完成“修复后真实 TUN + 长负载”的最终放行。
