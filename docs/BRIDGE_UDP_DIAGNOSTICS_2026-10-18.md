## 已复现的本机缺陷与修复

`SOCKSServer.udp` 原来忽略 UDP `Write` 的返回值。隔离用例注入一个明确返回 EPIPE、读取仍等待的 UDP 连接，旧行为失败：`failed UDP endpoint remained cached`。错误连接仍留在目标缓存中；修复后同一用例通过，失败报文只写入一次，下一次请求建立新的目标连接并取得回复。

现在只移除该失败目标的连接，保留 UDP association、其他目标和整个 VPN。使用已有的有界报文写入函数：零字节 ENOBUFS/EAGAIN 可等待原报文，最多 75 秒；部分写入、明确错误或到期则退出该目标。未知写入结果不重放报文，不回落到主机直连。取消会关闭正在等待的 UDP 连接，避免等待正常读期限。

该用例证明一个本机错误处理缺陷，**没有证明 0.11.12 在真实 VPN 上的 STUN 超时确实触发了这个分支**。实际根因仍需新的逐段诊断；不能以隔离成功替代真实网关验收。

## 有限诊断设计

普通报文不记录正文、地址、主机名、账号、Token、Cookie、原始错误或命令参数。只记录固定阶段、固定结果类别、errno、字节数、匿名连接编号和后台原始时间。一般 UDP I/O 错误有固定记录，但不会驱动 UI 断线或延长会话保护。

逐报文跟踪仅识别探针主动生成的 STUN 事务：`GCD1` 标记加随机、非零、JSON 可精确表示的 53 位编号。生产流量不加标记或改内容；诊断没有改变真实请求的 15 秒 UDP / 20 秒 HTTPS 期限。

| 事件阶段 | 观测边界 |
| --- | --- |
| `socks_receive` | 已解析 SOCKS UDP 测试请求 |
| `udp_write_start` / `udp_write` | 调用 / 完成用户态 UDP 连接写入 |
| `pipe_write_start` / `pipe_write` | 调用 / 完成发往 OpenConnect 的 UNIX packet socket 写入 |
| `pipe_read` | 从该通道读取到测试报文 |
| `stack_deliver` | 已调用用户态协议栈的报文输入，不能单独证明 UDP endpoint 已接收 |
| `udp_read` | UDP endpoint 已读到测试回复 |
| `socks_send` | 已向本地 SOCKS 客户端发送回复 |

`pipe_write` 成功只证明交给本地通道，不证明 OpenConnect 已读走，更不证明远端网关或外部服务收到。IPv4 分片与 IPv6 扩展头不做逐报文解析，正常转发仍由原协议栈处理。

桥接诊断使用 128 条非阻塞队列，每个桥接进程最多 8,192 条详细记录，并定期报告序号与丢弃计数。App 使用独立的 64 条诊断配额，写入 `~/Library/Logs/GoConnect/bridge.jsonl` 及一个轮转文件，各最多 1 MiB、权限 0600；不占用原 App 故障记录的排队配额。慢输出、日志拥塞和写盘失败可以损失诊断，不能让日志缺失被误判为丢包。取消和错误处理逻辑不依赖日志成功。

Swift 对阶段、结果和数字范围再次校验；未知字段不会写入日志。后台原始时间保留在 `details.timeMicros`，不能用经过 UI 排队之后的落盘时刻推断网络延迟。

## 使用与分析

新诊断只会在新候选组件实际运行后生效，当前已连接的 0.11.12 无法动态加载。SIP 保持启用，无需 DTrace 或向现有进程附加调试器。

在允许连接新候选后，将探针证据写到项目外的新目录：

```sh
python3 script/request_probe.py --output /absolute/new/evidence --interface en0 --seconds 900 --bridge-diagnostics
python3 script/analyze_bridge_probe.py --samples /absolute/new/evidence/samples.jsonl \
  --bridge-log "$HOME/Library/Logs/GoConnect/bridge.jsonl.1" \
  --bridge-log "$HOME/Library/Logs/GoConnect/bridge.jsonl"
```

网卡以实际物理出口为准；只有存在的轮转文件才应传入。UI 导出保留每个日志文件的有限尾部；完整事务分析应在本机使用原始私有文件，保留对应 App / bridge PID 和测试时间窗。

分析器将明确的桥接操作错误与“写入通道后未观察到回复”分开。日志轮转缺段、序号缺口、桥接或 App 端丢弃、测试窗口未覆盖时输出 `insufficient_trace`；不能据此认定服务器限流。STUN 错误应答被送达也会与没有回包分开。

## 验证与保护

- 旧实现失效缓存用例先失败、修复后通过；原报文不重放，下一次请求恢复。
- UDP 取消可中断等待；原 ENOBUFS/EAGAIN、阻塞写期限、真实错误和取消保护回归通过。
- 真实隔离双协议栈与 UNIX datagram 通道验证完整九阶段；普通、畸形、截断和分片报文不误记录，IPv4 / IPv6 标记解析通过。
- 人为阻塞日志消费者，转发调用仍不等待，队列有限且丢弃有记录。
- Swift 侧验证记录单独保存、0600 权限、固定字段及敏感 canary 不进入日志；解析器验证日志缺段时不得作肯定归因。
- 正式构建入口的 73 项 Swift 测试、Go race、14 项 TestLive 顶层用例和 10 项打包集成测试通过；需显式 root / 已安装 TUN 的场景仍按门禁跳过。
- 既有重复恢复、认证拒绝、地址变更、取消及 75 秒总恢复上限保留。未修改 30 秒租约 / 健康窗口、服务器策略、证书校验或 SIP。

## 长时间高负载结果

双路 FFmpeg 3840×2160 / H.264 软件编码同时运行 **620.812 秒**，302 次负载采样平均 CPU 占用 **99.50%**。两路渲染在所有采样中均存活；实际输出分别为 **394.633 秒 / 393.900 秒**，均超过三分钟。输出经 ffprobe 读回、SHA-256 留证后清除，共移除 1,478,737,162 字节的临时视频。

同时运行的 **0.11.13 隔离候选**使用包内 OpenConnect、真实 TLS/CSTP、UNIX datagram 通道及生产桥接代码，未创建系统 TUN 或改路由：

- 数据流持续 600.661 秒，568 轮 TCP 完整性与 UDP 往返全部通过，同一条 TCP 连接传输并核对 313,536,000 字节。

- 没有使用 UDP 重试掩盖失败。该网关为本机隔离夹具，不能替代真实网关。

并行观测的 **当前真实 VPN 仍为 0.11.12**，660.134 秒内 321 次状态采样均为 ready / VPN 可见，原有八个进程 PID 全程保持。渲染时间窗内 App 日志只有心跳、负载与内存压力事件，没有断线或重启事件。
